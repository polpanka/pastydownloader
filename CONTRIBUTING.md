# Contributing to PastyDownloader

Thanks for your interest in improving PastyDownloader.

PastyDownloader is a single [PySide6](https://www.qt.io/qt-for-python) codebase
that runs on Windows, macOS, Linux and Android. You paste a link — or a whole
batch — and the app detects the source and routes it to whatever downloads it
best: a generic HTTP fetcher, [yt-dlp](https://github.com/yt-dlp/yt-dlp) for the
sites it supports, or [FFmpeg](https://ffmpeg.org) for direct HLS/DASH streams.

For bug reports and feature requests, please search the
[issues](https://github.com/polpanka/pastydownloader/issues) first (including the
closed ones). If there are no duplicates, open a new issue with a clear
description. Issues without enough detail to act on may be closed.

For questions or general ideas, open a
[discussion](https://github.com/polpanka/pastydownloader/discussions).

## Bug report

Make sure the issue contains enough information to reproduce the problem:

- your OS and the app version (both are shown in the About screen)
- the exact link, or a minimal example, that triggers the bug
- the steps you took and what happened versus what you expected
- any error message shown by the app, and the relevant part of the log

A short screen recording is often the fastest way to explain a UI problem.

## Feature request

PastyDownloader stays deliberately small: paste a link, get the file, no
accounts, no options wizardry. It is a front end over existing extraction
engines, not a reimplementation of them.

- If a site does not download, that is almost always the extraction engine, not
  PastyDownloader. File it upstream (yt-dlp) unless the app is clearly routing
  the link to the wrong engine.
- Requests that add a settings screen, a new output pipeline, or a workflow that
  only a handful of users need are unlikely to be accepted. Prefer proposing the
  smallest possible change to the paste-and-download flow.
- Cross-platform matters: a feature that cannot work the same way on Windows,
  macOS, Linux and Android needs a good reason.

## Pull request

Before writing code, leave a comment on the relevant issue — or open one — and
describe the change you intend to make. This avoids two people solving the same
problem and lets the direction be agreed before the work is done.

Guidelines:

- Keep the diff focused on one thing. Unrelated cleanups belong in their own PR.
- Match the surrounding style: short comments, only the necessary *why*.
- Never put internal engine names ("yt-dlp", "FFmpeg") in user-facing strings —
  reuse the existing generic messages.
- Test on at least one desktop platform; note in the PR what you tested on.
- Update `CHANGELOG.md` if the change is user-visible.

## Building from source

### Desktop (Windows / macOS / Linux)

```sh
git clone https://github.com/polpanka/pastydownloader
cd pastydownloader/src
python3 -m venv .venv
. .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install PySide6 yt-dlp aiohttp requests certifi
python main.py
```

The application sources, build specs and helper scripts all live under `src/`;
the repo root keeps only docs, licensing and `.github/workflows/`. Python 3.11+
is recommended. FFmpeg is downloaded by the app on first use, so you do not need
it on your PATH to run from source.

Packaged builds are produced with the scripts in `src/`
(`src/build-appimage.sh`, `src/pysidedeploy.spec`) and by the GitHub Actions
workflows under `.github/workflows/` (each runs from `src/`).

### Android

The Android build is the same code, cross-compiled. It has its own toolchain
requirements (a Python 3.11 host, `python-for-android`, native FFmpeg) and a
number of platform quirks.

## AI contribution policy

Generative AI may be used for contributions, as long as you are fully aware of
what was generated, take full responsibility for it, and have made sure no
third-party copyrighted code is included.

AI-assisted contributions are welcome provided they follow these rules:

1. **Human responsibility:** You are 100% responsible for the code you submit.
   You must understand every line of the output.
2. **No untested submissions:** Do not submit AI-generated code you have not
   run, tested and verified locally.
3. **Disclosure:** If a significant part of your PR (a new module, a complex
   function) was generated by AI, say so in the PR description.
4. **Licensing:** Make sure the AI tool you use does not pull in code you have
   no right to contribute under the project's [LICENSE](LICENSE).
5. **Succinctness:** AI output tends to be verbose. Prune unnecessary comments
   and boilerplate before submitting.

**Failure to follow these guidelines may result in your pull request being
closed without review.**
